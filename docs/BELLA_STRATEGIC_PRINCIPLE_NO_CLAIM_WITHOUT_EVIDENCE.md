## 🔄 EVIDENCE HIERARCHY

### Tier 1: Strongest Evidence (Code + Tests + Metrics)
- Git repository (code inspection)
- Test execution logs (runnable verification)
- Metrics dashboard (real-time data)
- CI/CD pipeline results (automated verification)

**Example:**
> "Healthcare 1:3 reusability verified by:
> 1. Git history showing 3 products importing same Kernel
> 2. Static analysis showing 0 engine duplication
> 3. Test suite showing 100% contract compliance
> 4. Dependency graph showing proper layering"

---

### Tier 2: Strong Evidence (Case Studies + Documentation)
- Detailed case studies with metrics
- Architecture diagrams + dependency graphs
- ADR documents with rationale
- Review Board meeting minutes

**Example:**
> "Zero-Core-Change Test documented in case study:
> 1. Requirement specification
> 2. Development log (daily progress)
> 3. Code changes (Kernel + Product only)
> 4. Test results (before/after)
> 5. Effort tracking (hours per task)"

---

### Tier 3: Acceptable Evidence (Historical Data + Trends)
- Historical trends (e.g., cost curve)
- Comparative analysis (Product #1 vs #2 vs #3)
- Team velocity data
- Customer feedback

**Example:**
> "Marginal cost reduction trend:
> 1. Product #1 baseline established
> 2. Product #2 measured at 32% of baseline
> 3. Product #3 measured at 21% of baseline
> 4. Trend analysis shows decreasing curve"

---

### ❌ Tier 4: NOT Evidence (Not Acceptable)
- Projections without baseline data
- "We believe..." statements
- Theoretical designs without implementation
- Comparisons to other platforms without data
- Future roadmap without current evidence

## 💡 WHY THIS PRINCIPLE MATTERS

### For Technology Investors

**Traditional pitch:**
> "We have a platform that can build many Industry OS"

**Problem:** Claim without proof. Investor must take founder's word.

**Evidence-based pitch:**
> "Here's the code, tests, metrics, and case studies proving:
> 1. Reusability works (Healthcare 1:3)
> 2. Core is stable (Zero-Core-Change test)
> 3. Cost decreases (Marginal Cost Curve)
> 4. Factory works (New OS case study)
> 5. Migration works (Beauty Spa evidence)
> You can inspect the code, run the tests, and verify the metrics."

**Benefit:** Investor can verify claims. Builds trust. Reduces risk perception.

---

### For Due Diligence

**Traditional DD:**
- Investor asks: "Can you prove reusability?"
- Founder shows: Architecture diagrams
- Investor thinks: "Theoretical design, not proven"

**Evidence-based DD:**
- Investor asks: "Can you prove reusability?"
- Founder shows: 
  - Healthcare 1:3 dependency graph
  - Git history (3 products importing same Kernel)
  - Static analysis (0 duplication)
  - Test results (100% contract compliance)
- Investor thinks: "Verified with code, not claims"

**Benefit:** Faster DD, higher confidence, better valuation.

---

### For Team Discipline

**Without principle:**
- Team builds features without measurement
- Claims made without data
- Architecture drift undetected

**With principle:**
- Every claim requires evidence
- Measurement becomes habit
- Architecture compliance tracked
- Progress is verifiable

**Benefit:** Self-correcting organization. Problems detected early.

## 🚨 ENFORCEMENT

### Investor Communications

**All investor materials MUST follow this principle:**
- Pitch decks → cite evidence documents
- Technical presentations → show code/tests/metrics
- Q&A responses → reference specific case studies
- DD requests → provide verifiable data

**Forbidden:**
- ❌ "We can..." (future tense without baseline)
- ❌ "We believe..." (opinion without data)
- ❌ "Our platform will..." (projection without evidence)
- ❌ "We're the best..." (comparison without data)

**Required:**
- ✅ "We measured..." (past tense with data)
- ✅ "Evidence shows..." (reference to document)
- ✅ "Code proves..." (reference to repository)
- ✅ "Test results confirm..." (reference to logs)

---

### Internal Reviews

**Before any investor communication:**
1. Identify all claims
2. For each claim, verify evidence exists
3. If evidence missing → defer claim or gather evidence
4. If evidence weak → strengthen or remove claim
5. Review evidence trail (code → tests → metrics → docs)

**Checkpoint questions:**
- Can investor verify this claim by inspecting code? YES/NO
- Can investor run tests to confirm this claim? YES/NO
- Can investor see metrics dashboard for this claim? YES/NO
- Can investor read case study documenting this claim? YES/NO

**If ANY answer is NO → claim is not ready for investor communication**

---

### Post-Presentation Protocol

**After investor meeting:**
1. Document all questions asked
2. Identify claims that need stronger evidence
3. Create action items to gather missing evidence
4. Update evidence package
5. Send follow-up with evidence links

**Never:**
- ❌ Make promise without evidence path
- ❌ Claim capability without proof plan
- ❌ Commit to timeline without historical data
