## 1. Ownership Map & Architecture Decoupling

The `LedgerEngineService` owns the logic and database interactions for the core double-entry accounting records. It is vertical-agnostic and relies purely on financial primitives.

```
       [ Product Verticals / Clients ]
                      │
                      ▼
        [ Vertical Finance Bridge ] (Anti-Corruption Layer)
                      │
                      ▼ (Public Contracts / DTOs)
       [ Finance Orchestration Service ] (Core Orchestrator)
          │                            │
          ├── (1) Evaluates            └── (2) Resolves Post
          ▼                            ▼
   [ F5 Control Engine ]       [ F1 Ledger Engine ]
     (check limits)             (authoritative records)
```

### Table Ownership:
- `finance_accounts` (Write/Read)
- `finance_accounting_periods` (Write/Read)
- `finance_transactions` (Write/Read)
- `finance_transaction_lines` (Write/Read)
- `finance_outbox_events` (Write/Read)
- `finance_audit_trail` (Write-only)

## 2. Domain Invariants

The Ledger Engine enforces the following strict business constraints at the database and application levels:

| Invariant ID | Name | Description | Enforcement Level |
|---|---|---|---|
| **F-I-1** | Double-Entry Balance | $\sum \text{debit\_functional} = \sum \text{credit\_functional}$ exactly. | Application (BigInt math) + DB Transaction |
| **F-I-2** | Immutability | A POSTED transaction's financial content is immutable. Its lifecycle status may transition from POSTED → REVERSED through the authorized reversal operation. Direct edits of accounts, amounts, currencies, exchange rates, etc. are permanently blocked. | Application + DB Trigger |
| **F-I-3** | Idempotency | `(tenant_id, idempotency_key)` must be unique. Requires same idempotency_key + same request fingerprint/hash. Different request hash with same key throws IDEMPOTENCY_KEY_REUSE_CONFLICT. | Application Check + DB Unique Constraint |
| **F-I-4** | Period Lockout | Transactions cannot be posted to accounting periods with status `CLOSED` or `LOCKED`. Posting and Period Close/Lock serialize on the same accounting-period row. | Application Check + DB FOR UPDATE Lock |
| **F-I-5** | Decimal Math Safety | Floating-point numbers are prohibited. Money amounts are stored as string minor units, exchange rates are converted to BigInt using integer factor scaling with ROUND_HALF_UP rounding. | Application Types + DB NUMERIC(38, 0) |
| **F-I-6** | Sign & Mutual Exclusion | Line debit and credit must be $\ge 0$. A line cannot have both debit $> 0$ and credit $> 0$. | DB Check Constraints |
| **F-I-7** | Dimension Isolation | Business dimensions (location, project, BU, cost center) are referenced via opaque `dimension_id` and `dimension_type` strings. | Database columns (FKs omitted to preserve decoupling) |

## 3. Transaction Lifecycle & State Transitions

Transactions follow a strict state flow. Once a transaction reaches a terminal state, its values are permanently locked.

```
      [ DRAFT ] ──(postTransaction)──► [ POSTED ] (Immutable)
         │                                 │
         ├──(voidTransaction)              ├──(reverseTransaction)
         ▼                                 ▼
     [ VOIDED ]                        [ REVERSED ]
```

### State Transition Matrix:

| Current State | Target State: DRAFT | Target State: POSTED | Target State: REVERSED | Target State: VOIDED |
|---|---|---|---|---|
| **None (New)** | Allowed | Allowed (Direct Post) | Disallowed | Disallowed |
| **DRAFT** | Allowed (Update) | Allowed (Post) | Disallowed | Allowed (Void) |
| **POSTED** | Disallowed | Disallowed | Allowed (via Reversal) | Disallowed |
| **REVERSED** | Disallowed | Disallowed | Disallowed | Disallowed |
| **VOIDED** | Disallowed | Disallowed | Disallowed | Disallowed |

## 4. Error Code Catalog

To prevent generic failure messages, the F1 Ledger Engine returns distinct error codes:

| Error Code | HTTP Status | Description |
|---|---|---|
| `DOUBLE_ENTRY_IMBALANCE` | 400 | Sum of debits does not equal sum of credits in functional currency. |
| `PERIOD_NOT_FOUND` | 404 | No accounting period covers the transaction posted_at date. |
| `PERIOD_NOT_OPEN` | 400 | The accounting period is CLOSED or LOCKED. |
| `TRANSACTION_IMMUTABLE` | 400 | Attempted to update or delete a transaction that has already been POSTED or REVERSED. |
| `ACCOUNT_NOT_FOUND` | 404 | One or more account codes do not exist for this tenant. |
| `ACCOUNT_INACTIVE` | 400 | Tried to post a transaction to a deactivated financial account. |
| `DUPLICATE_IDEMPOTENCY_KEY` | 200 | Idempotency key already exists with identical payload. Returns original transaction ID. |
| `IDEMPOTENCY_KEY_REUSE_CONFLICT` | 409 | Idempotency key already exists but request payload/hash does not match. |
| `INVALID_AMOUNT` | 400 | Negative amount provided, or both debit and credit amounts are positive on the same line. |
| `CURRENCY_MISMATCH` | 400 | The transaction currency does not match line currencies, or functional conversion currency is invalid. |
| `MAXIMUM_REVERSAL_REACHED` | 400 | The transaction has already been reversed. A transaction can only be reversed once. |

## 5. DB Transaction Boundary

Every posting and reversal operation executes within a single database transaction to guarantee ACID consistency.

```
START DB TRANSACTION
  │
  ├── 1. Acquire row lock on target Accounting Period (ensuring serialized posting vs period close/lock)
  │      SELECT id, status FROM finance_accounting_periods WHERE ... FOR UPDATE
  │      Assert status == 'OPEN' (else abort/rollback)
  │
  ├── 2. Resolve & validate all Account IDs
  │      SELECT id, is_active FROM finance_accounts WHERE code IN (...) FOR SHARE
  │      Assert all active (else abort/rollback)
  │
  ├── 3. Assert idempotency
  │      SELECT id, status, request_hash FROM finance_transactions WHERE idempotency_key = ... FOR UPDATE
  │      If exists:
  │         If request_hash == current_hash: return existing transaction details & exit transaction early
  │         Else: raise IDEMPOTENCY_KEY_REUSE_CONFLICT & abort/rollback
  │
  ├── 4. Validate double-entry BigInt functional amount sum
  │      Assert Σ debit_functional == Σ credit_functional (else abort/rollback)
  │
  ├── 5. Insert header row into finance_transactions (storing idempotency_key & request_hash)
  │
  ├── 6. Insert lines into finance_transaction_lines
  │
  ├── 7. Insert audit trail row into finance_audit_trail
  │
  └── 8. Insert event envelope into finance_outbox_events
  │
COMMIT DB TRANSACTION
```

## 6. Transactional Outbox Strategy

To guarantee that event publication matches database state, Finance OS implements the Transactional Outbox Pattern:

```
BEGIN DB TRANSACTION
    │
    ├── 1. Insert Transaction Header
    ├── 2. Insert Transaction Lines
    ├── 3. Insert Audit Trail Row
    └── 4. Insert Outbox Event Envelope
            │
         COMMIT DB TRANSACTION
            │
            ▼
      Outbox Dispatcher (asynchronous processing loop)
            │
            ▼
       Event Bus (publish domain event)
```

This ensures that the outbox record is written in the same database transaction and committed atomically with the ledger writes. Only after a successful commit will the dispatcher read the event and publish it.

### Table Schema:
```sql
CREATE TABLE public.finance_outbox_events (
    id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
    tenant_id UUID NOT NULL REFERENCES public.tenants(id) ON DELETE CASCADE,
    event_id UUID NOT NULL UNIQUE, -- Immutable deduplication key for event bus consumers
    event_type VARCHAR(255) NOT NULL,
    payload JSONB NOT NULL, -- Stored as binary JSON (JSONB)
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING' CHECK (status IN ('PENDING', 'DISPATCHED', 'FAILED')),
    retry_count INT NOT NULL DEFAULT 0,
    error TEXT,
    processed_at TIMESTAMPTZ,
    last_attempt_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## 7. Idempotency Strategy

- **Verification Hook:** Every mutating call to F1 accepts an `idempotency_key` and the client payload.
- **Request Fingerprinting:** The service calculates a SHA-256 hash (`request_hash`) of the normalized transaction lines and header values (e.g. accounts, amounts, currencies).
- **Race Condition Guard:** The database has a unique index on `(tenant_id, idempotency_key)`.
- **Handling Duplicate Requests:**
  - If a transaction is found with the same `idempotency_key` for this tenant:
    - Compare the incoming `request_hash` with the stored `request_hash`.
    - If they MATCH: return the existing transaction ID and state with `success: true` (HTTP 200).
    - If they DO NOT MATCH (different payload under the same key): abort the call and throw `IDEMPOTENCY_KEY_REUSE_CONFLICT` (HTTP 409).
  - This prevents client retries with different payloads under the same key from corrupting Ledger entries.

## 8. Reversal & Voiding Strategy

### Reversal of POSTED Transactions (Immutable Audit Trail)
- Direct mutation of posted financial lines is forbidden. Only lifecycle status, `reversed_at`, and `reversal_of` metadata can be transitioned.
- To reverse a transaction `T` (status `POSTED`):
  1. Retrieve transaction `T` and verify it has not already been reversed (`status` must be `POSTED`, `reversal_of` must be null).
  2. Determine target reversal date: `p_reversal_date` (defaulting to `NOW()`).
  3. Resolve the OPEN accounting period at `p_reversal_date`. Reversal is a new financial transaction and must post to an OPEN period at the reversal time. It does **not** automatically use the original transaction's period. If original period is CLOSED, reversal posts to current OPEN period; if target date period is CLOSED, it is rejected with `PERIOD_NOT_OPEN`.
  4. Create a new transaction `R` with `status: 'POSTED'`, `transaction_type: 'REVERSAL'`, `reversal_of: T.id`, and a client-provided `idempotencyKey` specifically for this reversal operation.
  5. For every line in `T`, create a line in `R` with **swapped debits and credits** (functional and transaction currencies).
  6. In the same database transaction, update `T.status = 'REVERSED'`.
  7. Write audit logs and outbox events for both the state change of `T` and the creation of `R`.
  8. Enforce invariant: **One original POSTED transaction can be reversed at most once**. Any subsequent reversal request throws `MAXIMUM_REVERSAL_REACHED` (or `TRANSACTION_IMMUTABLE`).

### Voiding of DRAFT Transactions
- A transaction in `DRAFT` status has not affected ledger balances.
- It can be marked `VOIDED` in place.
- No reversal lines are generated.

## 9. Accounting Period Strategy

- Every transaction carries a `posted_at` date.
- The service maps `posted_at` to the correct accounting period:
  ```sql
  SELECT id, status FROM finance_accounting_periods 
  WHERE tenant_id = :tenant_id 
    AND period_start <= :posted_at 
    AND period_end >= :posted_at
  FOR UPDATE;
  ```
- If the period status is `CLOSED` or `LOCKED`, the transaction is rejected. Period close/lock and posting serialize on this row lock to prevent race conditions.

## 10. Multi-Currency & Decimal Precision Math

- Functional currency (default: `VND`) is the base reporting currency of the ledger.
- String minor amounts are converted to `BigInt` inside the application layer.

### Conversion Logic with ROUND_HALF_UP:
Let $A_{trans}$ be the transaction currency amount in minor units.  
Let $R$ be the exchange rate decimal representation (e.g. `24500.000000` with 6 decimal places).  
The functional currency amount $A_{func}$ is calculated using half-up rounding.

$$\text{functional\_amount} = \text{truncate}\left(\frac{A_{trans} \times \text{rate\_integer} + \frac{\text{rate\_factor}}{2}}{\text{rate\_factor}}\right)$$

Using BigInt:
```typescript
const rateScale = 6;
const rateFactor = BigInt(10 ** rateScale); // 1000000
const rateInteger = BigInt(rate.replace('.', '')); // "24500.000000" -> 24500000000

const transAmount = BigInt(money.amount_minor);
const halfFactor = rateFactor / 2n;

// Multi-currency ROUND_HALF_UP implementation
const funcAmount = (transAmount * rateInteger + halfFactor) / rateFactor;

const functionalMoney: Money = {
  amount_minor: funcAmount.toString(),
  currency: functionalCurrency
};
```

## 11. Test Matrix (Verification Gates F-4 to F-8)

| Gate | Test Case Description | Expected Result |
|---|---|---|
| **Gate F-4** | Post balanced entries (debits = credits) | Transaction is saved with status `POSTED`. |
| **Gate F-4** | Post imbalanced entries (debits $\ne$ credits) | Throws `DOUBLE_ENTRY_IMBALANCE` and aborts transaction. |
| **Gate F-5** | Attempt to direct UPDATE or DELETE a `POSTED` transaction row | Blocked by database/application guard; throws `TRANSACTION_IMMUTABLE`. |
| **Gate F-5** | Execute reversal on a `POSTED` transaction | Original transaction marked `REVERSED`; new `REVERSAL` transaction created with swapped debits/credits. |
| **Gate F-6** | Send duplicate `postTransaction` concurrently with the same `idempotency_key` | Only one transaction created; duplicate call returns the first transaction's details safely. |
| **Gate F-7** | Post transaction with `posted_at` falling into a `CLOSED` period | Throws `PERIOD_NOT_OPEN` and rolls back transaction. |
| **Gate F-8** | Audit log and Outbox records presence inside the transaction | If the outbox write fails (e.g., mock error), the entire ledger write is rolled back, leaving no orphan ledger records. |
| **Gate F-1.3.A** | Concurrent Idempotency (Test 1) | Fire 100 concurrent requests with the same tenant and idempotency key. Verify exactly 1 transaction created, and other 99 returned the same transaction ID without duplicates. |
| **Gate F-1.3.B** | Concurrent Period Close (Test 2) | Run `postTransaction` concurrently with `closePeriod` for the same period. Assert row locking serializes operations: transaction either posts before close, or is rejected after close. |
| **Gate F-1.3.C** | Outbox Duplicate Delivery (Test 3) | Dispatch event, simulate dispatcher crash before outbox state is updated to DISPATCHED. Re-dispatch and verify consumer does not process financial side-effects twice due to event deduplication on event_id. |
