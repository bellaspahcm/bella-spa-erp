## 🔒 DECISION 1: APPROVAL ID SOURCE

### Problem Statement

Current approval creation is MANUAL (interactive CLI script). Workflow needs `approval_id` to call BDGF, but how to obtain it?

### Options Considered

| Option | Pros | Cons | Security Risk |
|--------|------|------|---------------|
| **A. Manual pre-approval** | Preserves human gate, auditable | Requires pre-deployment step | ✅ LOW |
| B. Auto-generate approval | Fully automated, no human step | **Bypasses governance**, self-authorization | ❌ CRITICAL |
| C. Lookup by migration_id | Simple integration | Ambiguous if multiple approvals exist | ⚠️ MEDIUM |
| D. Separate approval service | Clean API boundary | Requires new service (out of scope) | ✅ LOW |

### Decision: OPTION A — MANUAL PRE-APPROVAL ✅

**Workflow receives `approval_id` as input parameter (workflow_dispatch).**

**Implementation:**
```yaml
on:
  workflow_dispatch:
    inputs:
      approval_id:
        description: 'Approval ID from bella_migration_approval'
        required: true
        type: string
```

**Workflow:**
1. Human creates approval using `record-human-go-approval.mjs`
2. Approval script outputs: `approval_id = <UUID>`
3. Human triggers workflow with `approval_id` parameter
4. Workflow passes `approval_id` to BDGF wrapper

**Invariant Preserved:**
```
Human Decision
      ↓
Manual Approval Creation
      ↓
approval_id (UUID)
      ↓
Workflow Input (explicit)
      ↓
BDGF Verification
```

**No automation bypass** — approval CANNOT be self-generated by workflow.

### Rationale

**Why Option A:**
- ✅ Preserves human-in-the-loop authority
- ✅ No self-authorization risk
- ✅ Explicit approval_id (auditable)
- ✅ Aligns with current R4 contract (manual approval)
- ✅ Simple implementation (no new services)

**Why NOT Option B (Auto-generate):**
- ❌ **CRITICAL SECURITY VIOLATION:** Workflow would self-authorize
- ❌ Bypasses human governance gate
- ❌ Violates I0 invariant (no self-approval)
- ❌ Creates automation bypass path

**Why NOT Option C (Lookup):**
- ⚠️ Ambiguous if multiple approvals exist for same migration_id
- ⚠️ Race condition: multiple workflows could find same approval
- ⚠️ Implicit approval selection (less auditable)

**Trade-off Accepted:**
- Manual step required (human creates approval first)
- Not fully automated end-to-end
- **Benefit:** Governance integrity preserved

## 🔒 DECISION 2: MIGRATION DISCOVERY

### Problem Statement

Workflow needs to know which migration file(s) to execute. How to discover them?

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A. Git diff detection** | Deterministic, commit-scoped | Requires git operations |
| B. Scan all migrations | Simple | **DANGEROUS** (re-executes old migrations) |
| C. Manifest file | Explicit control | Extra metadata file |
| D. Workflow input | Direct specification | Manual, error-prone |

### Decision: OPTION A — GIT DIFF DETECTION ✅

**Workflow scans `git diff --name-only` for changed files in `supabase/migrations/**`.**

**Implementation:**
```bash
# Detect changed migration files
git diff --name-only ${{ github.event.before }}..${{ github.sha }} \
  | grep '^supabase/migrations/.*\.sql$' \
  || echo ""
```

**Output:** List of changed .sql files (e.g., `supabase/migrations/20260825120000_add_column.sql`)

### Rationale

**Why Option A:**
- ✅ Deterministic (exact files changed in commit)
- ✅ Commit-scoped (only new/changed migrations)
- ✅ Traceable (linked to commit SHA)
- ✅ Aligns with Supabase migration convention
- ✅ No external metadata needed

**Why NOT Option B (Scan all):**
- ❌ **DANGEROUS:** Would re-execute all migrations
- ❌ Violates idempotency assumptions
- ❌ No commit scoping

**Why NOT Option C (Manifest):**
- Adds complexity (extra file to maintain)
- Redundant with git history

## 🔒 DECISION 3: MIGRATION ID DERIVATION

### Problem Statement

Approval uses `migration_id` (e.g., "M001"). Workflow detects filename (e.g., `20260825120000_add_column.sql`). How to map them?

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A. Filename = migration_id** | Simple, deterministic | Filename must match approval |
| B. Commit SHA = migration_id | Unique, cryptographic | Approval must know commit SHA before push |
| C. Lookup table | Flexible | Extra metadata |
| D. Extract from migration file | Self-contained | Requires parsing SQL |

### Decision: OPTION A — FILENAME = CANONICAL IDENTITY ✅

**Migration filename (without `.sql`) becomes `migration_id`.**

**Convention:**
```
Filename: 20260825120000_add_column.sql
         ↓
migration_id: "20260825120000_add_column"
```

**Requirement:** Approval creation script MUST use same filename-based `migration_id`.

**Example Workflow:**
```bash
# Detect migration file
MIGRATION_FILE="supabase/migrations/20260825120000_add_column.sql"

# Derive migration_id
MIGRATION_ID=$(basename "$MIGRATION_FILE" .sql)
# Result: "20260825120000_add_column"

# Verify approval exists for this migration_id
# (BDGF wrapper will verify via R4 contract)
```

### Rationale

**Why Option A:**
- ✅ Deterministic (filename → migration_id mapping)
- ✅ No external dependencies
- ✅ Aligns with Supabase timestamp-based naming
- ✅ Human-readable
- ✅ No parsing required

**Why NOT Option B (Commit SHA):**
- Approval must be created AFTER push (chicken-egg problem)
- Commit SHA unknown at approval creation time

**Constraint:** Approval script must derive `migration_id` from filename consistently.

**Updated Approval Workflow:**
```bash
# In record-human-go-approval.mjs
const migrationFile = "supabase/migrations/20260825120000_add_column.sql";
const migrationId = path.basename(migrationFile, '.sql');
// migrationId = "20260825120000_add_column"
```

## 🔒 DECISION 4: MULTIPLE MIGRATIONS PER COMMIT

### Problem Statement

What if one commit contains 3 new migration files? Execute all? Require separate approvals?

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A. BLOCK (one only)** | Simple, clear audit | Less flexible |
| B. Execute all (one approval) | Batch efficiency | Ambiguous approval binding |
| C. Require multiple approvals | Explicit per-migration | Complex coordination |
| D. Execute first only | Partial execution | Incomplete deployment |

### Decision: OPTION A — BLOCK IF MULTIPLE DETECTED ✅

**Phase 4B.2 enforces: ONE migration per commit.**

**Implementation:**
```bash
# Count detected migrations
MIGRATION_COUNT=$(git diff --name-only $BEFORE..$AFTER \
  | grep '^supabase/migrations/.*\.sql$' \
  | wc -l)

if [ "$MIGRATION_COUNT" -gt 1 ]; then
  echo "❌ ERROR: Multiple migrations detected ($MIGRATION_COUNT files)"
  echo "   Phase 4B.2 requires one migration per commit."
  echo "   Each migration must have separate commit and approval."
  exit 1
fi
```

**Error Message:**
```
❌ BLOCKED: Multiple migrations detected

Detected files:
- supabase/migrations/20260825120000_add_column_a.sql
- supabase/migrations/20260825120001_add_column_b.sql
- supabase/migrations/20260825120002_add_column_c.sql

Requirement: Each migration requires separate commit and approval.

Action: Split into 3 commits, create 3 approvals.
```

### Rationale

**Why BLOCK:**
- ✅ Eliminates ambiguity (which approval for which migration?)
- ✅ Clear audit trail (1 commit = 1 migration = 1 approval)
- ✅ Simpler verification (no batch coordination)
- ✅ Aligns with forward-only principle (incremental changes)
- ✅ Easier rollback analysis (per-migration granularity)

**Why NOT allow multiple:**
- ❌ Approval binding ambiguity:
  - One approval for all 3 migrations?
  - Or 3 separate approvals?
- ❌ Execution order ambiguity:
  - What if migration 2 fails?
  - Execute migration 3 anyway?
- ❌ Hash binding complexity:
  - Approval binds to ONE migration_hash
  - How to bind to 3 hashes?

**Constraint Enforced:**
```
ONE commit
    ↓
ONE migration file
    ↓
ONE migration_id
    ↓
ONE approval
    ↓
ONE migration_hash
    ↓
ONE execution
```

**Phase 5 Consideration:** If batch migrations needed in future, create separate batch workflow with multi-approval orchestration (out of scope for 4B.2).

## 🔒 DECISION 5: MISSING APPROVAL SCENARIO

### Problem Statement

Workflow detects migration file, but no approval exists in database. Auto-create approval? Block execution?

### Options Considered

| Option | Pros | Cons | Security Risk |
|--------|------|------|---------------|
| **A. FAIL-CLOSED / BLOCK** | Preserves governance | Manual approval required | ✅ NONE |
| B. Auto-create approval | Fully automated | **Bypasses human gate** | ❌ CRITICAL |
| C. Request approval workflow | Trigger approval request | Complex orchestration | ⚠️ MEDIUM |
| D. Log warning, continue | Non-blocking | **Allows unauthorized execution** | ❌ CRITICAL |

### Decision: OPTION A — FAIL-CLOSED / BLOCK ✅

**If no approval found → BLOCK execution immediately.**

**Implementation:**
```bash
# After deriving migration_id, check approval exists
# (BDGF wrapper will verify, but workflow checks early)

echo "🔍 Checking approval for migration: $MIGRATION_ID"

# Query database (read-only check)
APPROVAL_CHECK=$(psql "$DATABASE_URL" -tAc "
  SELECT approval_id FROM bella_migration_approval
  WHERE migration_id = '$MIGRATION_ID'
    AND status = 'approved'
    AND expires_at > NOW()
  LIMIT 1
")

if [ -z "$APPROVAL_CHECK" ]; then
  echo "❌ BLOCKED: No valid approval found"
  echo ""
  echo "Migration: $MIGRATION_ID"
  echo "Status: No approved, non-expired approval exists"
  echo ""
  echo "Required Action:"
  echo "1. Create approval using: node scripts/bdgf/record-human-go-approval.mjs"
  echo "2. Re-run workflow with approval_id parameter"
  exit 1
fi
```

**Error Message:**
```
❌ BLOCKED: No valid approval found

Migration ID: 20260825120000_add_column
File: supabase/migrations/20260825120000_add_column.sql
Hash: a3f5d8c2... (computed from file)

No approval record found with:
- migration_id = "20260825120000_add_column"
- status = "approved"
- expires_at > NOW()

Required Action:
1. Create approval:
   node scripts/bdgf/record-human-go-approval.mjs \
     --migration-id="20260825120000_add_column" \
     --environment="production"

2. Re-run workflow with approval_id

Governance Contract: No execution without explicit human approval.
```

### Rationale

**Why FAIL-CLOSED:**
- ✅ **Preserves human governance gate** (no automation bypass)
- ✅ Explicit approval required (no implicit authorization)
- ✅ Aligns with R4 contract (approval = authorization)
- ✅ Fail-safe (any doubt → block)
- ✅ Clear error message (actionable)

**Why NOT auto-create:**
- ❌ **CRITICAL VIOLATION:** Workflow self-authorizes
- ❌ Bypasses human decision
- ❌ Violates I0 invariant (no self-approval)
- ❌ Creates automation bypass

**Why NOT log warning:**
- ❌ **CRITICAL VIOLATION:** Allows unauthorized execution
- ❌ Approval becomes optional (defeats purpose)
- ❌ Governance becomes advisory (not enforced)

**Invariant Preserved:**
```
NO approval
    ↓
NO authorization
    ↓
NO execution

Approval REQUIRED
```

### Hash Binding Verification

**Scenario: Migration file changes after approval**

```
Time T1: Human approves migration A
         approved_hash = SHA256(migration_A_content)

Time T2: Developer modifies migration A
         current_hash = SHA256(modified_content)

Time T3: Workflow executes
         BDGF verifies: approved_hash ≟ current_hash
         
         If approved_hash ≠ current_hash:
              ↓
           BLOCK (I1 violation)
```

**Invariant:** Approval cryptographically bound to exact migration content.

## 📋 CONTRACT IMPLICATIONS

### 4B.2 Contract Must Define

**Based on these decisions:**

1. **Workflow Input:**
   - `approval_id` (workflow_dispatch parameter, required)
   - Commit SHA (automatic)

2. **Migration Discovery Logic:**
   - Git diff: `$BEFORE..$AFTER`
   - Filter: `supabase/migrations/*.sql`
   - Validation: Exactly 1 file (error if 0 or >1)

3. **Migration ID Derivation:**
   - Extract: `basename <file> .sql`
   - Example: `20260825120000_add_column.sql` → `"20260825120000_add_column"`

4. **Approval Verification (Early Check):**
   - Query: Find approval by `migration_id` + `status='approved'`
   - BLOCK if not found

5. **BDGF Invocation:**
   - Command: `node scripts/bdgf/execute-migration-wrapper.mjs <approval_id> <migration_file>`
   - Secrets: `DATABASE_EXECUTOR_URL`, `GATE_SIGNING_KEY`

6. **Error Handling:**
   - Multiple migrations → FAIL with error message
   - No approval → FAIL with actionable instructions
   - BDGF error → FAIL and propagate
   - Hash mismatch → FAIL (BDGF handles)

7. **Success Output:**
   - Approval ID (for audit)
   - Migration file executed
   - Execution result (from BDGF)
