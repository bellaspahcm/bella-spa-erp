# H0.5: Reuse Decision Gate Framework

**Date:** 2026-09-15  
**Status:** 📐 ACTIVE FRAMEWORK  
**Purpose:** Guide architecture decisions for capability reuse vs. build-new

---

## 🎯 Core Principle

> **"Kernel mới = phương án cuối cùng, KHÔNG PHẢI phương án mặc định."**

Before building any new capability, **exhaust all reuse options** through this decision gate.

## 📋 Gate-by-Gate Decision Criteria

### GATE 1: Does Capability Exist?

**Question:** Is there an existing platform capability that does this?

**Search Locations:**
1. `src/platform/core/*` - Core platform primitives
2. `src/platform/healthcare/*` - Healthcare OS engines
3. `src/platform/finance/*` - Finance engines
4. `src/platform/[vertical]/*` - Other vertical platforms
5. Contract Registry - All registered contracts

**Evidence Required:**
- Contract interface definition
- Implementation file path
- Test coverage status
- Documentation

**Decision:**
- **YES** → Proceed to GATE 2
- **NO** → Proceed to GATE 5

---

### GATE 2: Semantic Compatibility?

**Question:** Do the domain concepts semantically map to the existing capability?

**Evaluation Criteria:**

#### Strong Semantic Overlap (≥70%)
**Example:** Healthcare "Bed" → Haircut "Cutting Station"
- Both are **physical resources**
- Both have **availability status** (available, occupied, maintenance)
- Both require **allocation/release** lifecycle
- Both support **feature-based queries** (e.g., "has_mirror", "VIP_room")

**Decision:** ✅ REUSE with semantic adapter (10-15% new code)

---

#### Weak Semantic Overlap (<50%)
**Example:** Healthcare "Lab Order" → Haircut "Walk-in Queue"
- Lab Order is **asynchronous** (order → wait → result)
- Queue is **synchronous** (enter → wait → serve)
- Different lifecycle semantics
- Different state machines

**Decision:** Proceed to GATE 3 (check if contract extensible)

---

### GATE 3: Contract Extensible?

**Question:** Can we extend the contract without breaking existing consumers?

**Extension Patterns:**

#### ✅ Safe Extensions
1. **Add optional fields** to request/response DTOs
2. **Add new methods** to contract interface (backwards compatible)
3. **Add new event types** to event registry
4. **Add enum values** (if not exhaustively matched)

**Example:**
```typescript
// BEFORE (Healthcare)
interface EncounterCreateRequest {
  patientId: string;
  encounterClass: 'AMB' | 'EMER' | 'IMP';
}

// AFTER (Extended for Haircut)
interface EncounterCreateRequest {
  patientId: string;
  encounterClass: 'AMB' | 'EMER' | 'IMP' | 'HAIRCUT_WALKIN' | 'HAIRCUT_SCHEDULED'; // ADD
  stylistPreference?: string; // NEW OPTIONAL FIELD
}
```

**Decision:** 🔧 EXTEND contract (20% new code)

---

#### ❌ Breaking Extensions
1. **Remove required fields** (breaks existing calls)
2. **Change method signatures** (existing consumers fail)
3. **Rename events** (breaks event subscribers)

**Decision:** Cannot extend → Proceed to GATE 4

---

### GATE 4: Configuration Sufficient?

**Question:** Can we achieve the requirement through **configuration alone** without code changes?

**Configuration Patterns:**

#### ✅ Configuration-Only Changes
1. **Enum values:** Add `OrgUnitType = 'haircut_salon'`
2. **Permission strings:** Add `'haircut:appointment:read'`
3. **Feature flags:** Enable/disable capabilities per tenant
4. **Template definitions:** Add receipt template for haircut service

**Example:**
```typescript
// NO CODE CHANGE - Just configuration
const haircutPermissions = [
  'haircut:appointment:read',
  'haircut:appointment:write',
  'haircut:stylist:assign',
];
```

**Decision:** ⚙️ CONFIGURE only (5% effort - documentation/config files)

---

#### ❌ Configuration Insufficient
Requires business logic changes, new validation rules, different workflows

**Decision:** Return to GATE 3 → Extend capability (20% new code)

---

### GATE 5: Pattern Exists in Different Vertical?

**Question:** Does a similar pattern exist in another vertical that we can adapt?

**Search Strategy:**
1. Review other vertical platforms (Healthcare, Real Estate, Finance)
2. Look for **analogous workflows** (e.g., "Resource Allocation")
3. Check if **pattern is extractable** to platform primitive

**Examples of Cross-Vertical Patterns:**
- **Appointment Booking** (Healthcare Encounter) → Haircut Appointment
- **Commission Calculation** (Real Estate Agent) → Stylist Commission
- **Resource Allocation** (Hospital Bed) → Cutting Station

**Decision:**
- **YES, pattern exists** → Create **Semantic Adapter Layer** (15% new code)
- **NO pattern found** → Proceed to BUILD NEW

---

### BUILD NEW: Last Resort

**When to Build:**
1. No existing capability found (GATE 1: NO)
2. No semantic compatibility (GATE 2: NO)
3. Contract not extensible (GATE 3: NO)
4. No analogous pattern (GATE 5: NO)

**Requirements Before Building:**
1. ✅ **Architecture Change Request (ACR)** filed
2. ✅ **Architecture Decision Record (ADR)** written
3. ✅ **Contract design** reviewed by Architecture Council
4. ✅ **Test strategy** (estimate 40+ test suites for new kernel)
5. ✅ **Migration impact** assessed (if replacing existing database logic)

**Approval Process:**
- **Human Architect Review** required
- **Architecture Council** sign-off
- **Risk assessment** documented

**Decision:** 🆕 BUILD NEW (100% new code, high effort)

## 🧪 Worked Examples

### Example 1: Stylist Assignment

**Request:** "Assign stylist to customer appointment"

**GATE 1:** Does capability exist?  
→ ✅ YES: Healthcare `Encounter.assignProvider` exists

**GATE 2:** Semantic compatibility?  
→ ✅ YES:
- "Provider" (Doctor/Nurse) → "Stylist"
- "Encounter" → "Appointment"
- Assignment logic is identical

**Decision:** ✅ **REUSE** with semantic adapter  
**Code New:** 10% (adapter layer only)

---

### Example 2: Walk-in Queue Management

**Request:** "Manage walk-in customer queue with position tracking"

**GATE 1:** Does capability exist?  
→ ❌ NO: No queue management engine found

**GATE 5:** Pattern exists?  
→ ⚠️ PARTIAL: Healthcare Emergency Department triage (found in comments, no implementation)

**GATE 5 Decision:** No production-ready pattern  
**Decision:** 🆕 **BUILD NEW** (Queue Engine)  
**Code New:** 100%  
**Requirements:**
- ACR for Queue Engine capability
- ADR documenting queue semantics (FIFO, priority-based, time-based)
- Contract design with event publishing

---

### Example 3: Service Catalog

**Request:** "Define haircut services (cut, styling, wash, color)"

**GATE 1:** Does capability exist?  
→ ✅ YES: Healthcare `Order Engine` (medications, lab tests, procedures)

**GATE 2:** Semantic compatibility?  
→ ✅ YES (70% overlap):
- "Order" → "Service"
- "Order Type" (medication, lab) → "Service Type" (cut, style, wash)
- Lifecycle is similar (draft → active → completed)

**GATE 3:** Contract extensible?  
→ ✅ YES: Add `serviceCategory: 'haircut'` field

**Decision:** 🔧 **EXTEND** Order Engine contract  
**Code New:** 15% (haircut-specific service types + validation rules)

---

### Example 4: Multi-Tenancy for Salons

**Request:** "Support multiple salon branches with hierarchy"

**GATE 1:** Does capability exist?  
→ ✅ YES: `OrgUnitEngine` with hierarchy management

**GATE 2:** Semantic compatibility?  
→ ✅ YES (95% overlap):
- "Branch" → "Salon Branch"
- "Department" → "Floor/Section"
- Hierarchy semantics identical

**GATE 4:** Configuration sufficient?  
→ ✅ YES: Add enum value `OrgUnitType = 'haircut_salon'`

**Decision:** ⚙️ **CONFIGURE** only  
**Code New:** 0% (configuration file change only)

---

### Example 5: Stylist Commission Calculation

**Request:** "Calculate stylist commission based on services performed"

**GATE 1:** Does capability exist?  
→ ✅ YES: Real Estate `CommissionContract` (agent commission on property sales)

**GATE 2:** Semantic compatibility?  
→ ⚠️ PARTIAL (60% overlap):
- "Agent" → "Stylist"
- "Contract Sale" → "Service Revenue"
- **BUT:** Different calculation rules (tiered % vs. flat rate per service)

**GATE 3:** Contract extensible?  
→ ✅ YES: Add `commissionType: 'per_service' | 'percentage_tiered'`

**Decision:** 🔧 **EXTEND** Commission Contract  
**Code New:** 25% (new commission calculation rules + haircut domain mapping)

## 🚨 Red Flags: When to Escalate

Escalate to **Human Architect Review** if:

1. **Semantic Overlap Ambiguous** (50-70% range)
   - Example: "Is Bed → Station a good mapping?"
   - Risk: May force wrong abstraction

2. **Contract Extension Breaks Invariants**
   - Example: Adding optional field that changes validation rules
   - Risk: Silent breakage of existing consumers

3. **Multiple Paths Possible**
   - Example: Extend Order Engine OR build Service Catalog from scratch
   - Risk: Premature optimization or over-engineering

4. **Cross-Kernel Dependencies**
   - Example: Haircut Queue depends on Healthcare Encounter AND Logistics Inventory
   - Risk: Tight coupling across OS boundaries

5. **Performance or Scale Concerns**
   - Example: Reusing Encounter Engine for high-frequency walk-in appointments
   - Risk: Not designed for that scale

## 🔐 Governance Rules

### Rule 1: Document All Decisions
Every capability must have a decision log entry with:
- Which gates were evaluated
- Evidence consulted (file paths, line numbers)
- Rationale for final decision
- Architect approval (for BUILD NEW decisions)

### Rule 2: Prefer Earlier Gates
Bias toward gates with **lower code new %**:
- GATE 4 (Configure: 5%) > GATE 2 (Reuse: 10%) > GATE 3 (Extend: 20%) > BUILD (100%)

### Rule 3: Challenge "No" Answers
If GATE 1 returns NO, **search harder**:
- Check contract registry
- Grep codebase for similar patterns
- Review ADRs for rejected capabilities
- Ask: "Could this be generalized?"

### Rule 4: Semantic Overlap ≥70% = Reuse
If semantic compatibility ≥70%, **bias toward reuse** with adapter layer rather than building new.

### Rule 5: No Kernel Without ACR
Any "BUILD NEW" decision that creates a new Kernel capability requires:
1. Architecture Change Request (ACR)
2. Architecture Council approval
3. ADR with rationale

---

## 🎓 Anti-Patterns to Avoid

### ❌ Anti-Pattern 1: "Not Invented Here"
**Symptom:** Rejecting reuse because "it doesn't exactly fit"  
**Fix:** If semantic overlap ≥60%, bias toward adapter layer

### ❌ Anti-Pattern 2: "Force-Fit Abstraction"
**Symptom:** Reusing capability with <50% semantic overlap  
**Fix:** Return to GATE 5 or BUILD NEW - don't force wrong abstraction

### ❌ Anti-Pattern 3: "Premature Optimization"
**Symptom:** Building generic capability for one use case  
**Fix:** Follow Rule of Three - wait for 3rd use case before abstracting

### ❌ Anti-Pattern 4: "Configuration Overload"
**Symptom:** 20+ config flags to make generic capability work  
**Fix:** This is a signal to BUILD NEW - configuration complexity = wrong abstraction

### ❌ Anti-Pattern 5: "Silent Dependency Coupling"
**Symptom:** Extending contract without updating all consumers  
**Fix:** Use event versioning, deprecation notices, consumer registry
