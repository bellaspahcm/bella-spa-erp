# F5.6 Architecture Finding A3-001: Account Code Is Not Semantic Identity

> **Finding ID:** A3-001  
> **Date:** 2026-08-16  
> **Severity:** HIGH  
> **Type:** Architectural Principle Discovery  
> **Status:** CONFIRMED — Candidate for AR-011

---

## Executive Summary

**Finding:**
> **Account code cannot be used as semantic identity in a multi-regime, multi-tenant Finance OS.**

**Discovered During:**
- A.3 Semantic Research (TK 142/244 verification)
- Correction: A3-COR-001
- Conflict: C-004

**Impact:**
- Invalidates account-code-based semantic registry design
- Requires 5-layer canonical semantic model
- Enables multi-tenant COA customization within legal bounds
- AR-011 candidate: "Account Code Is Not Semantic Identity"

**Production Impact:**
- ✅ **ZERO** (discovered before schema design)

**Architectural Value:**
- 🟢 **HIGH** (prevented fundamental design error)

## Background

### Original Design Assumption (v0.1)

**Semantic Registry Concept:**
```
accounting_semantic_registry (
    regime_code,
    account_code,        ← ASSUMED: account code = semantic identity
    business_event,
    semantic_classification,
    ...
)
```

**Implicit Assumption:**
> "Account codes are stable semantic identifiers across regimes and tenants."

**Why This Seemed Reasonable:**
1. TT133 and TT99 both use 3-digit account codes
2. Many codes appear similar (331, 141, 111, etc.)
3. Big4 guidance discusses "account mapping" between regimes
4. Account code is visible identifier in financial statements

## Discovery Process

### Trigger: TK 142/244 Semantic Conflict

**Initial Claim (Crowe Vietnam 2016):**
```
TT133:
- TK 142 = Short-term prepaid expenses
- TK 244 = Long-term prepaid expenses

TT99:
- TK 242 = Prepaid expenses (merged)

Classification: MERGED
```

**Primary Source Verification (Thư Viện Pháp Luật — TT133 Điều 38):**
```
TT133:
- TK 142 = Chi phí trả trước (Prepaid expenses)
- TK 244 = Ký quỹ, ký cược dài hạn (Long-term deposits/pledges)

TK 244 ≠ Prepaid expenses
```

**Key Insight:**
> **Same account code structure (142, 244, 242) ≠ Same semantic category**

---

### Critical Evidence: TT99/2025 Điều 11

**From Thư Viện Pháp Luật — TT99/2025 Điều 11:**
> "Doanh nghiệp được điều chỉnh tên, số hiệu, cấu trúc và nội dung tài khoản để phù hợp với đặc điểm hoạt động và yêu cầu quản lý của doanh nghiệp."

**Translation:**
> "Enterprises may modify account names, numbers, structure, and content to match operational characteristics and management requirements."

**Implication:**
> **Within legal bounds, tenants can customize Chart of Accounts.**

**Architectural Consequence:**
```
Tenant A (wholesale):
PREPAID_EXPENSE → Account 242

Tenant B (manufacturing):
PREPAID_EXPENSE → Account 2421 (subdivided)

Tenant C (SME):
PREPAID_EXPENSE → Account 242X (custom structure)

Same semantic, different account codes.
```

## Finding Statement

### Core Finding

**Statement:**
> **Account code MUST NOT be used as the canonical identity of an accounting semantic. Semantic identity must exist independently of regulatory regime, tenant, tenant COA, account number, and account name.**

**Why This Matters:**

1. **Regime Evolution:**
   - TT133 → TT99 → Future circulars
   - Account codes may change
   - Semantics remain stable

2. **Tenant Customization:**
   - Multi-tenant platform
   - Each tenant may customize COA within legal bounds
   - Same semantic → different account codes per tenant

3. **Business Event Consistency:**
   - "Record vendor prepayment" = same business event
   - May map to different accounts depending on:
     - Regulatory regime
     - Tenant COA design
     - Industry-specific requirements

4. **Historical Reconstruction:**
   - Transaction in 2025 under TT133 with account 331
   - Query in 2030 must know:
     - Semantic = VENDOR_PREPAYMENT
     - Account realization at that time = 331
     - Current account may be different
   - Cannot rely on current account code to interpret historical semantic

---

### Invalidated Design

**WRONG MODEL:**
```sql
CREATE TABLE accounting_semantic_registry (
    regime_code VARCHAR(20),
    account_code VARCHAR(10),      -- ❌ WRONG: Used as semantic key
    business_event VARCHAR(100),
    semantic_classification VARCHAR(50),
    ...
);
```

**Why Wrong:**
- Account code ≠ stable across regimes
- Account code ≠ stable across tenants
- Account code ≠ semantic identity

**Example Failure:**
```
Tenant A: Account 242 = PREPAID_EXPENSE
Tenant B: Account 242 = PREPAID_EXPENSE_SHORT_TERM
                        Account 2421 = PREPAID_EXPENSE_LONG_TERM

Same code, different semantic granularity.
```

---

### Correct Architecture

**RIGHT MODEL:**

```
┌─────────────────────────────────────┐
│     Regulatory Regime                │
│     (TT133, TT99, future)            │
│     Defines legal requirements       │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│     Canonical Accounting Semantic    │
│     Regime-independent identifiers   │
│     PREPAID_EXPENSE                  │
│     EMPLOYEE_ADVANCE                 │
│     VENDOR_PREPAYMENT                │
│     CASH_ON_HAND                     │
│     TRADE_PAYABLE                    │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│     Enterprise Accounting Policy     │
│     Recognition, measurement rules   │
│     Policy versioning                │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│     Tenant Chart of Accounts         │
│     Customizable within legal bounds │
│     Tenant A: PREPAID_EXPENSE → 242  │
│     Tenant B: PREPAID_EXPENSE → 2421 │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│     Posting Rules Engine             │
│     Resolve semantic → account       │
│     Generate posting instructions    │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│     F1 Finance Kernel                │
│     Receives: account_id, Dr, Cr     │
│     Does NOT interpret semantic      │
│     Regime-agnostic                  │
└─────────────────────────────────────┘
```

**Characteristics:**
1. **Canonical Semantic Layer** — regime-independent, tenant-independent
2. **Separation of Concerns** — semantic ≠ policy ≠ account realization
3. **Tenant Customization Boundary** — COA customizable, semantic not
4. **Kernel Agnostic** — Finance Kernel doesn't interpret semantic/regime/policy

## Architectural Principles

### AR-011 Candidate: Account Code Is Not Semantic Identity

**Proposed Invariant:**

> **AR-011: Account Code Is Not Semantic Identity**
> 
> Account code MUST NOT be used as the canonical identity of an accounting semantic. Semantic identity must exist independently of:
> - Regulatory regime
> - Tenant
> - Tenant Chart of Accounts
> - Account number
> - Account name
> 
> **Rationale:** Account codes may change due to regulatory evolution or tenant customization. Semantic identity must remain stable to support historical reconstruction, multi-regime operation, and multi-tenant COA flexibility.

**Enforcement:**
- ❌ No `regime × account_code` as primary key in semantic registry
- ✅ Canonical semantic identifiers (e.g., `PREPAID_EXPENSE`, `EMPLOYEE_ADVANCE`)
- ✅ Account realization as mapping layer (semantic → account per regime/tenant/policy)

---

### AR-012 Candidate: Tenant COA Customization Boundary

**Proposed Invariant:**

> **AR-012: Tenant COA Customization Boundary**
> 
> Tenant may customize account code, name, and structure only through a regulatory-policy-constrained mapping layer. Customization MUST NOT alter canonical accounting semantic identity.
> 
> **Rationale:** TT99/2025 Điều 11 permits COA customization within legal bounds. Finance OS must support this while preserving semantic integrity across tenants.

**Enforcement:**
- ✅ Tenant COA stored per tenant
- ✅ Semantic → Account mapping per tenant
- ❌ Tenant cannot redefine semantic meaning
- ✅ Regulatory compliance validation before tenant COA activation

## Impact Analysis

### What Changes

**1. Semantic Model Design**

**Before:**
```
regime × account_code → semantic
```

**After:**
```
Canonical Semantic (regime-independent)
    ↓
Regime Requirement Mapping
    ↓
Tenant Policy Configuration
    ↓
Tenant COA Mapping
    ↓
Account Realization
```

---

**2. Historical Reconstruction**

**Before:**
```sql
-- WRONG: Assumes account code = semantic
SELECT * FROM journal_entries
WHERE account_code = '331';
-- Problem: What if 331 meant different things in different regimes/tenants?
```

**After:**
```sql
-- RIGHT: Stores semantic context
SELECT * FROM journal_entries
WHERE semantic_id = 'VENDOR_PREPAYMENT'
  AND regime_code = 'TT133'
  AND policy_version = 'v1.0';
-- Unambiguous: semantic + regime + policy
```

---

**3. Multi-Tenant Support**

**Before:**
```
All tenants use same account codes.
-- Problem: Cannot customize COA per tenant.
```

**After:**
```
Each tenant configures:
- Tenant COA (customizable)
- Semantic → Account mapping
- Subject to regulatory constraints

Bella validates:
- Mapping complies with regime requirements
- Semantics preserved
```

---

**4. Posting Rules**

**Before:**
```javascript
// WRONG: Hard-code account numbers
if (businessEvent === 'vendor_prepayment') {
    debit('331');  // What if tenant uses 3311?
    credit('111');
}
```

**After:**
```javascript
// RIGHT: Resolve semantic to account
const semanticContext = {
    event: 'VENDOR_PREPAYMENT',
    regime: tenant.currentRegime,
    policy: tenant.currentPolicy
};

const accounts = accountResolver.resolve(semanticContext, tenant);
debit(accounts.prepaymentAsset);
credit(accounts.cash);
```

---

### What Stays the Same

**Finance Kernel (F1-F4):**
- ✅ No changes required
- ✅ Still receives: `account_id`, `debit`, `credit`
- ✅ Still enforces: balanced entries, immutability, audit trail
- ✅ Remains regime-agnostic

**Why:**
> "Finance Kernel stores context but does not interpret context."

**Posting Instruction Format:**
```json
{
    "transaction_id": "T12345",
    "lines": [
        {
            "account_id": 1001,  // Resolved by Posting Rules layer
            "debit": 1000000,
            "credit": 0
        },
        {
            "account_id": 2001,
            "debit": 0,
            "credit": 1000000
        }
    ],
    "context": {
        "regime_code": "TT99",
        "policy_version": "v1.0",
        "semantic_event": "VENDOR_PREPAYMENT"
    }
}
```

Kernel persists `context` as metadata, does NOT interpret it.

## Risks Mitigated

**Risk 1: Account Code Conflicts**
- **Without AR-011:** Different tenants may use same code for different semantics
- **With AR-011:** Semantic identity independent, no conflict

**Risk 2: Regime Migration Complexity**
- **Without AR-011:** Must migrate all account codes in data
- **With AR-011:** Update mapping layer, data untouched

**Risk 3: Historical Ambiguity**
- **Without AR-011:** Old account codes may not match current semantic
- **With AR-011:** Semantic + account realization both stored, no ambiguity

**Risk 4: Tenant Customization Limits**
- **Without AR-011:** Cannot allow COA customization (breaks semantic)
- **With AR-011:** COA customizable, semantic preserved
