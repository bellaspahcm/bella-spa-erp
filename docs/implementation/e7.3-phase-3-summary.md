## Key Design Decisions

### 1. Query-Based Lineage (Not Graph DB)
**Decision:** Lineage queries operate on filtered movement arrays  
**Rationale:**
- Simple, predictable, testable
- No external graph database dependency
- Performance acceptable for typical lot/serial volumes
- Can optimize later if needed (without API changes)

**Note:** E7.3 traceability operations are read-only and side-effect-free with respect to domain state. They receive data and return results without mutating entities or executing workflows.

### 2. Cycle Safety Over Speed
**Decision:** Visited set tracking + depth limits  
**Rationale:**
- Prevents infinite loops
- Reports cycles explicitly
- Predictable resource usage
- Deterministic termination

### 3. Explicit Broken Chain Reporting
**Decision:** Return `brokenLinks[]` array, never fabricate data  
**Rationale:**
- Transparency > convenience
- Product decides how to handle gaps
- Compliance requires accuracy
- No silent failures

### 4. Movement Status Filtering
**Decision:** Only include `COMPLETED` movements in lineage  
**Rationale:**
- `PENDING` movements not yet executed
- `CANCELLED` movements never happened
- Clear, consistent semantics
