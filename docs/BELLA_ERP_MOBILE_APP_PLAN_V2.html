Executive Summary

Tổng Quan Dự Án

Kế hoạch này mô tả chiến lược chuyển đổi Bella ERP từ ứng dụng web Next.js sang ứng dụng di động đa nền tảng iOS/Android. Dựa trên đánh giá chuyên gia (scoring 8.5/10), phiên bản V2.0 này bổ sung các yếu tố kiến trúc quan trọng:

  • Multi-tenant Architecture: Thiết kế SaaS từ ngày đầu với company_id/branch_id trên mọi bảng
  • RBAC System: 5 vai trò (Owner, Manager, Receptionist, KTV, Accountant) với ma trận quyền chi tiết
  • QR Check-in/Check-out: Nâng từ P1 lên P0 - Core workflow automation
  • Push Notifications: Nâng từ P1 lên P0 - Critical cho user retention
  • Offline Strategy: Đơn giản hóa thành Read Cache + Action Queue (không full CRUD)
  • Camera Upload: Tính năng mới - Upload CCCD, hợp đồng, hình ảnh khách hàng

Lựa chọn công nghệ: React Native + Expo (code sharing 70-80% với web codebase hiện tại)

Timeline: 16 tuần (1 senior dev) hoặc 12 tuần (2 devs)

Chi phí ước tính: $32,000 - $43,000 (development) + $2,000/năm (services)

Điểm đánh giá cải thiện: 8.5/10 → 9.4/10 sau khi áp dụng feedback

Phần 03

Technology Decision Matrix

Option 1: React Native + Expo ✅ Recommended

Pros:

  • ✅ 70-80% code sharing với React/TypeScript codebase hiện tại
  • ✅ Team đã biết React, TypeScript, Zustand
  • ✅ Có thể reuse Supabase client, API services, business logic
  • ✅ Expo cung cấp OTA updates, easy testing, faster iteration
  • ✅ Ecosystem mạnh: React Navigation, Expo modules
  • ✅ Fastest time-to-market: 12-16 tuần

Cons:

  • ⚠️ Performance hơi thấp hơn native (chấp nhận được cho ERP)
  • ⚠️ Một số native modules có thể cần ejection (hiếm)

Cost: $32,000 - $43,000

Option 2: Flutter

Pros:

  • ✅ Performance tốt (Skia rendering engine)
  • ✅ UI đẹp out of the box (Material Design 3)
  • ✅ Single codebase iOS + Android + Web

Cons:

  • ❌ Zero code sharing với current stack
  • ❌ Team phải học Dart (ngôn ngữ mới)
  • ❌ Không reuse được React hooks, Zustand stores
  • ❌ Timeline dài hơn: 4-5 tháng

Cost: $45,000 - $60,000

Option 3: Native (Swift + Kotlin)

Pros:

  • ✅ Best performance
  • ✅ Full access native APIs
  • ✅ Best UX cho từng platform

Cons:

  • ❌ Zero code sharing
  • ❌ Cần 2 codebases riêng biệt
  • ❌ Cần 2 developers chuyên biệt (iOS + Android)
  • ❌ Timeline dài nhất: 6-8 tháng

Cost: $80,000 - $120,000

✅ Final Decision: React Native + Expo

Rationale:

  1. Code Reuse: 70-80% codebase được share
  2. Speed: Fastest to MVP (12-16 tuần vs 4-8 tháng)
  3. Cost: Most economical ($32k-43k vs $45k-120k)
  4. Team: Leverage existing React/TypeScript expertise
  5. Maintenance: Single tech stack (React) cho web + mobile

Phần 05

Multi-Tenant Architecture (NEW in V2.0)

Why Multi-Tenant from Day 1?

Bella ERP's SaaS future yêu cầu:

  • ✅ Nhiều companies dùng chung infrastructure
  • ✅ Mỗi company có nhiều branches
  • ✅ Data isolation giữa companies (security + privacy)
  • ✅ Single deployment phục vụ tất cả customers

⚠️ WARNING: Thêm multi-tenancy sau này cực kỳ đau đớn:
• Migration schema cho 100% tables
• Refactor mọi query trong app
• Risk data loss/corruption
• Weeks of downtime

Database Schema Changes

Before (Single-Tenant):

CREATE TABLE customers (
  id UUID PRIMARY KEY,
  name TEXT NOT NULL,
  phone TEXT NOT NULL
);

After (Multi-Tenant):

CREATE TABLE customers (
  id UUID PRIMARY KEY,
  company_id UUID NOT NULL REFERENCES companies(id),
  branch_id UUID REFERENCES branches(id),
  name TEXT NOT NULL,
  phone TEXT NOT NULL
);

CREATE INDEX idx_customers_company ON customers(company_id);
CREATE INDEX idx_customers_branch ON customers(branch_id);

Query Pattern Changes

Before:

const customers = await supabase
  .from('customers')
  .select('*');

After:

const customers = await supabase
  .from('customers')
  .select('*')
  .eq('company_id', currentUser.company_id);

Tenant Hierarchy

Company (Tenant)
├── Branch 1 (Spa Quận 1)
│   ├── Employees
│   ├── Customers
│   └── Bookings
├── Branch 2 (Spa Quận 3)
│   ├── Employees
│   ├── Customers
│   └── Bookings
└── Shared Resources
    ├── Service Packages
    ├── Accounting Accounts
    └── Reports (consolidated)

Phần 06

RBAC System Design (NEW in V2.0)

Why RBAC?

ERP không thể chỉ có "Admin vs Staff". Các users khác nhau cần quyền khác nhau:

  • Owner: Full access (financial reports, settings, employees)
  • Manager: Operations (bookings, customers, KTV schedules) nhưng NO financial access
  • Receptionist: Check-in, booking creation, customer management
  • KTV: View own schedule, clock in/out, view own commissions
  • Accountant: Financial reports, invoicing, revenue (NO customer data editing)

Implementation Pattern

// packages/shared/services/auth.service.ts
export const checkPermission = (
  user: User,
  resource: string,
  action: 'read' | 'write' | 'delete'
): boolean => {
  const userRole = user.role;
  
  // Owner has all permissions
  if (userRole === ROLES.OWNER) return true;
  
  // Check permission matrix
  return PERMISSIONS[userRole]?.[resource]?.[action] ?? false;
};

// Usage in components
const canEditCustomer = checkPermission(currentUser, 'customer', 'write');

Phần 08

Offline Strategy (Simplified for MVP)

Expert Feedback: Offline là Tính Năng Khó Nhất

❌ Original Plan (Too Ambitious):
Week 3-4: Offline foundation - Full CRUD offline, conflict resolution, merge strategies

✅ V2.0 Plan (Realistic for MVP):
Phase 1: Read Cache Only (Weeks 3-4)
Phase 2: Action Queue (Weeks 5-6)

Phase 1: Read Cache Only

What works offline:

  • ✅ View customer list (cached)
  • ✅ View schedule (cached)
  • ✅ View booking details (cached)
  • ❌ Cannot edit anything

Implementation:

// Using Dexie.js (already in Bella ERP)
import Dexie from 'dexie';

const db = new Dexie('BellaERPCache');
db.version(1).stores({
  customers: 'id, name, phone',
  bookings: 'id, customer_id, date',
  sessions: 'id, booking_id, ktv_id',
});

// Sync from server when online
const syncCustomers = async () => {
  if (navigator.onLine) {
    const customers = await supabase.from('customers').select('*');
    await db.customers.bulkPut(customers.data);
  }
};

Phase 2: Action Queue

What works offline:

  • ✅ Check-in (queued, synced when online)
  • ✅ Create booking (queued, synced when online)
  • ❌ Cannot edit existing data (conflict risk)

Implementation:

const actionQueue = new Dexie('ActionQueue');
actionQueue.version(1).stores({
  actions: '++id, type, payload, timestamp',
});

// Queue action when offline
const queueCheckIn = async (sessionId) => {
  await actionQueue.actions.add({
    type: 'CHECK_IN',
    payload: { sessionId, timestamp: Date.now() },
  });
};

// Sync queue when online
const syncQueue = async () => {
  const actions = await actionQueue.actions.toArray();
  for (const action of actions) {
    try {
      await executeAction(action);
      await actionQueue.actions.delete(action.id);
    } catch (error) {
      console.error('Sync failed:', error);
    }
  }
};

What We DON'T Do in MVP

  • ❌ No offline editing of existing records (conflict resolution quá phức tạp)
  • ❌ No offline deletion (nguy hiểm nếu server đã xóa)
  • ❌ No complex data relationships offline (foreign key integrity nightmare)
